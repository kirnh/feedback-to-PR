How the before/after clip is made

The flow is written by the agentIt ships a small Maestro script in the PR that opens the changed screen using testIDs or deep links. It runs on the baseline first. If it fails there, the demo is marked unavailable instead of showing a wrong clip.
Fallbacks, in orderSide-by-side clip, then screenshots, then "no visual change" with the diff summary and test evidence. Logic and test-only changes take the last path.
Health app: fixtures onlyRecordings run on seeded fake data, never real data. The installer will not enable demos without an app-side demo mode.
iPhone lateriOS simulators need macOS runners at about ten times the price per minute. Android first; iPhone clips on demand.

Dashed means unverified. I could not confirm that the emulator and the open-source Maestro runner work on plain GitHub runners, or whether private-repo release assets can host the clips. A one-to-two-day spike answers both before anything else is built on them.

2. First platform for clipsDefault: Android only.
3. Where clips liveDefault: GitHub release assets first; Cloudflare R2 if private access fails.
4. Feedback entry pointDefault: a row in the app's Settings.
5. Installer guinea pigDefault: a fresh sample app, not MediSync.

"One click" is honest only in the third tier. The first tier is one command, the second is two or three clicks, and the third needs a hosted service with accounts and billing. I recommend the first tier now. The full detail is in docs/PLAN-integration.md in the repo.
